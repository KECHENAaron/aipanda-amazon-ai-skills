# 预算：先验证约束，再讨论扩大或收缩

低 ACOS 不能单独推出应该加预算。先看成熟样本、同范围效率、是否出现可追溯的预算约束，以及承接能力和观察期；若约束未知，保持缺证。广告已经暂停、流量归属不清、规则同时改动时，不把预算增减当成孤立动作。

平均日预算不是每日硬上限。官方不同资料给出不同上浮示例，公告也说明账户可配置；不能把某个比例写成适用于所有账户的固定日封顶。不要仅凭“当天花费达到预算”推断耗尽状态，也不要把预算乘天数当成保证的总花费上限。

预算耗尽信号在本协议中是逐日声明，程序不独立核实。如果没有声明的约束日期、信号不完整、样本或效率不支持，增加预算候选被阻断。减少预算也需选定指标支持的偏离证据；本工具并未覆盖库存应急、清仓等所有决策目标。

跨活动分配时，先明确所选范围的总资源边界、不同角色与可承接对象，再查哪里确实受约束、哪里只是缺流量或承接不足。不按课程中的固定份额或按最低 ACOS 机械分配；不同活动的点击和归因口径也不能混算。本脚本只复核一个匿名活动的提议，不自动做跨活动资金转移。

预算规则、日程规则与实际可用资金要分开。规则可能改变生效配置，读取到一个显示值不代表排除了后续自动变更。脚本将未建模的预算规则保留阻断；当前值与规则状态仍须本地实时复查。

公开案例只有常量构造的预算和指标，无真实商品、店铺、成本费用账本。利润核对不进入预算方法。
